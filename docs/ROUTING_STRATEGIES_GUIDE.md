## 路由策略概述

### 什么是路由策略？

路由策略是 LMRouter 在接收到 AI 模型请求时，决定将请求发送到哪个供应商账号的规则和算法。

**类比说明：**
```
就像打车软件的派单逻辑：
- 你叫车（发起 AI 请求）
- 系统有多个司机可选（多个供应商账号）
- 路由策略决定派哪个司机（选择哪个账号）

不同的策略就像不同的派单规则：
- 速度优先 → 派最近的司机
- 价格优先 → 派收费最低的司机
- 综合平衡 → 考虑距离、价格、评分
- 轮询 → 依次轮流派单
```

### 为什么需要路由策略？

1. **成本优化** - 不同供应商价格差异巨大（可能相差 10 倍）
2. **性能保障** - 不同供应商速度差异明显（TTFT 从 100ms 到 5000ms）
3. **可靠性提升** - 避免单个账号故障或限流
4. **负载均衡** - 合理分配请求到多个账号

## 核心概念

### 关键指标

#### 1. TTFT (Time to First Token) - 首字延迟
```
定义：从发送请求到收到第一个 token 的时间
单位：毫秒 (ms)

示例：
- 优秀：100-200ms  （用户几乎感觉不到延迟）
- 良好：200-500ms
- 一般：500-1000ms
- 较差：1000-2000ms
- 很差：>2000ms

影响因素：
- 服务器地理位置
- 服务器负载
- 网络延迟
- 模型大小
```

#### 2. 吞吐量 (Throughput)
```
定义：每秒生成的 token 数量
单位：tokens/second (tps)

示例：
- 优秀：80-100 tps
- 良好：50-80 tps
- 一般：30-50 tps
- 较差：<30 tps

适用场景：
- 高吞吐量适合长文本生成
- 低吞吐量也可以用于短对话
```

#### 3. 成本 (Cost)
```
计算公式：
总成本 = (输入 token 数 × 输入单价) + (输出 token 数 × 输出单价)

示例：
假设请求：
- 输入：1000 tokens
- 输出：500 tokens

供应商 A：
- 输入：$0.0005 / 1K tokens
- 输出：$0.0015 / 1K tokens
- 总成本：1000 × 0.0005 + 500 × 0.0015 = $0.5 + $0.75 = $1.25

供应商 B：
- 输入：$0.0002 / 1K tokens
- 输出：$0.0006 / 1K tokens
- 总成本：1000 × 0.0002 + 500 × 0.0006 = $0.2 + $0.3 = $0.5

成本差异：1.25 / 0.5 = 2.5 倍
```

#### 4. 成功率 (Success Rate)
```
定义：请求成功完成的百分比
单位：% (0-100)

示例：
- 优秀：>99%
- 良好：95-99%
- 一般：90-95%
- 较差：<90%

失败原因：
- API 密钥失效
- 账号余额不足
- 触发速率限制
- 服务器错误
- 超时
```

#### 5. RPM/TPM 限制
```
RPM (Requests Per Minute)：每分钟请求数限制
TPM (Tokens Per Minute)：每分钟 token 数限制

示例：
账号 A：RPM 限制 100，TPM 限制 200,000
账号 B：RPM 限制 500，TPM 限制 1,000,000

使用策略：
- 短对话（低 token）→ 关注 RPM
- 长文本（高 token）→ 关注 TPM
```

## 四种策略详解

### 1️⃣ Nitro - 速度优先 ⚡

#### 核心思想
**追求最快的响应速度，不惜成本。**

#### 评分算法
```
总分 = TTFT 得分 × 70% + 吞吐量得分 × 30%

TTFT 得分计算：
- 100ms 以下 → 100 分
- 5000ms 以上 → 0 分
- 中间值线性插值

示例：
- 150ms → 99 分（优秀）
- 500ms → 90 分（良好）
- 1000ms → 79 分（一般）
- 2000ms → 56 分（较差）
- 3000ms → 34 分（很差）

吞吐量得分计算：
- 100 tps 以上 → 100 分
- 10 tps 以下 → 0 分
- 中间值线性插值
```

#### 适用场景

✅ **强烈推荐：**
- 实时聊天机器人
- 语音助手
- 实时翻译
- 代码补全
- 交互式游戏

❌ **不推荐：**
- 批量文档处理
- 后台任务
- 离线分析
- 成本敏感场景

#### 实际案例

**场景：在线客服聊天机器人**

```
用户：你好，我想查询订单
Nitro 选择：OpenAI 官方（TTFT 120ms）
           ↓
        响应速度：120ms（用户几乎无感）

如果选择 Floor 策略：
           ↓
        可能选择：廉价供应商（TTFT 800ms）
        响应速度：800ms（用户明显感觉延迟）

用户体验差异：120ms vs 800ms = 6.7 倍
```

#### 优缺点

**优点：**
- ✅ 最佳用户体验
- ✅ 最快的首字响应
- ✅ 适合实时交互

**缺点：**
- ❌ 成本较高
- ❌ 可能不考虑可靠性
- ❌ 不适合批量处理

---

### 2️⃣ Floor - 价格优先 💰

#### 核心思想
**追求最低成本，牺牲部分性能。**

#### 评分算法
```
价格得分计算：
- 总成本 < $0.0001 → 100 分
- 总成本 > $0.1 → 0 分
- 中间值线性插值

示例：
假设 1000 输入 + 500 输出 tokens

供应商 A（$1.25）→ 12 分（昂贵）
供应商 B（$0.50）→ 57 分（中等）
供应商 C（$0.10）→ 99 分（便宜）
```

#### 适用场景

✅ **强烈推荐：**
- 批量文档摘要
- 后台数据分析
- 离线任务处理
- 成本敏感应用
- 非营利项目

❌ **不推荐：**
- 实时聊天
- 用户交互场景
- 对延迟敏感的应用

#### 实际案例

**场景：批量处理 1000 篇文章摘要**

```
每篇文章平均：2000 输入 tokens + 200 输出 tokens

使用 Nitro 策略：
- 单篇成本：$2.50
- 1000 篇总成本：$2,500
- 处理时间：2 小时

使用 Floor 策略：
- 单篇成本：$0.50
- 1000 篇总成本：$500
- 处理时间：5 小时

成本节省：$2,000 (80%)
时间增加：3 小时（可接受，因为是后台任务）
```

#### 优缺点

**优点：**
- ✅ 最低成本
- ✅ 适合批量处理
- ✅ 预算可控

**缺点：**
- ❌ 响应较慢
- ❌ 用户体验较差
- ❌ 可能可靠性较低

---

### 3️⃣ Balanced - 综合平衡 ⚖️

#### 核心思想
**在价格、速度、可靠性之间取得最佳平衡。**

#### 评分算法
```
总分 = 价格得分 × 35% + 速度得分 × 35% + 可靠性得分 × 30%

价格得分：
- 计算方式同 Floor 策略
- 价格越低，得分越高

速度得分：
- TTFT 70% + 吞吐量 30%
- 计算方式同 Nitro 策略

可靠性得分：
- 成功率 50% + 可用性 30% + 错误率 20%
- 综合评估稳定性

示例：
供应商 A：
- 价格：60 分（中等）
- 速度：85 分（良好）
- 可靠性：95 分（优秀）
- 总分：60×0.35 + 85×0.35 + 95×0.3 = 21 + 29.75 + 28.5 = 79.25

供应商 B：
- 价格：95 分（便宜）
- 速度：40 分（较慢）
- 可靠性：70 分（一般）
- 总分：95×0.35 + 40×0.35 + 70×0.3 = 33.25 + 14 + 21 = 68.25

选择：供应商 A（综合更优）
```

#### 适用场景

✅ **强烈推荐：**
- 大多数通用应用
- 生产环境默认选择
- 不确定用哪个策略时
- 需要稳定性的场景

❌ **不推荐：**
- 极端追求速度（改用 Nitro）
- 极端追求低价（改用 Floor）

#### 实际案例

**场景：企业级 AI 助手**

```
需求：
- 响应要快（但不能太贵）
- 成本要合理（但不能太慢）
- 必须稳定（不能经常失败）

Balanced 策略选择：
- 价格：中等偏上（$0.75/请求）
- 速度：良好（TTFT 300ms）
- 可靠性：优秀（99.5% 成功率）

综合评估：虽然不是最快也不是最便宜，但整体最优
```

#### 权重调整

```typescript
// 可以自定义权重（默认：价格 35%，速度 35%，可靠性 30%）

// 场景 1：更关注成本
setWeights({ price: 0.5, speed: 0.25, reliability: 0.25 })

// 场景 2：更关注速度
setWeights({ price: 0.25, speed: 0.5, reliability: 0.25 })

// 场景 3：更关注可靠性
setWeights({ price: 0.25, speed: 0.25, reliability: 0.5 })
```

#### 优缺点

**优点：**
- ✅ 综合考虑多方面
- ✅ 适合大多数场景
- ✅ 风险分散
- ✅ 可定制权重

**缺点：**
- ❌ 不是任何单项最优
- ❌ 需要调参才能发挥最大价值

---

### 4️⃣ Round Robin - 轮询 🔄

#### 核心思想
**简单公平地依次分配请求到每个账号。**

#### 工作原理
```
假设有 3 个账号：A、B、C

请求 1 → A
请求 2 → B
请求 3 → C
请求 4 → A
请求 5 → B
请求 6 → C
...循环往复

特点：
- 不考虑性能
- 不考虑价格
- 不考虑负载
- 简单轮询
```

#### 适用场景

✅ **强烈推荐：**
- 账号性能相近
- 简单负载均衡
- 测试环境
- 临时使用

❌ **不推荐：**
- 账号性能差异大
- 需要优化成本
- 需要优化性能
- 生产环境推荐用 Balanced

#### 实际案例

**场景：多个同配置账号**

```
你有 5 个 OpenAI 账号，配置完全相同：
- 相同的速率限制
- 相同的价格
- 相同的性能

使用 Round Robin：
- 简单有效
- 平均分配负载
- 避免单个账号过载
```

#### 优缺点

**优点：**
- ✅ 实现简单
- ✅ 负载平均
- ✅ 无需复杂计算

**缺点：**
- ❌ 不考虑性能差异
- ❌ 不考虑成本
- ❌ 不考虑健康状态
- ❌ 可能选择不健康的账号

## 策略选择指南

### 决策树

```
开始
  ↓
是否需要实时响应？
  ├─ 是 → 使用 Nitro ⚡
  └─ 否 ↓
      是否对成本敏感？
        ├─ 是 → 使用 Floor 💰
        └─ 否 ↓
            是否账号性能相近？
              ├─ 是 → 使用 Round Robin 🔄
              └─ 否 → 使用 Balanced ⚖️（推荐）
```

## 实际应用案例

### 案例 1：AI 写作助手

**需求分析：**
- 用户输入提示词，需要快速看到开头
- 全文生成需要时间，速度要求降低
- 用户希望成本可控
- 需要稳定可靠

**推荐方案：Balanced 策略**

```
理由：
1. 速度重要（用户等待开头）
2. 但不是极端重要（全文生成可以慢）
3. 成本需要考虑（用户会大量使用）
4. 稳定性很重要（不能经常失败）

Balanced 配置：
- 价格权重：35%
- 速度权重：35%
- 可靠性权重：30%

实际效果：
- TTFT：300ms（可接受）
- 成本：比 Nitro 节省 50%
- 成功率：99.2%（非常稳定）
```

### 案例 2：批量 SEO 文章生成

**需求分析：**
- 后台批量生成 10000 篇文章
- 不需要实时响应
- 成本是主要考虑因素
- 可以接受较慢速度

**推荐方案：Floor 策略**

```
理由：
1. 成本优先（10,000 篇文章，成本差异巨大）
2. 速度不重要（后台任务）
3. 可以容忍偶尔失败

Floor 配置：
- 选择价格最低的供应商

实际效果：
- Nitro 策略：$25,000，2 天完成
- Floor 策略：$5,000，5 天完成
- 节省：$20,000 (80%)
- 时间增加：3 天（可接受）
```

### 案例 3：实时客服聊天机器人

**需求分析：**
- 用户实时对话
- 延迟严重影响体验
- 成本不是主要考虑
- 需要高可用性

**推荐方案：Nitro 策略**

```
理由：
1. 速度是第一位（用户体验）
2. 实时对话不能有延迟
3. 成本可以接受（每次对话 token 不多）

Nitro 配置：
- TTFT 权重：70%
- 吞吐量权重：30%

实际效果：
- TTFT：120ms（用户几乎无感）
- 每次对话成本：$0.10（可接受）
- 用户满意度：⭐⭐⭐⭐⭐
```

### 案例 4：内部测试环境

**需求分析：**
- 多个开发人员测试
- 账号配置相同
- 简单即可

**推荐方案：Round Robin 策略**

```
理由：
1. 账号性能相同
2. 需要平均分配负载
3. 不需要复杂策略

实际效果：
- 负载均匀分配
- 实现简单
- 满足测试需求
```

## 附录：技术细节

### 评分函数

```typescript
// Nitro 策略评分
score = ttftScore * 0.7 + throughputScore * 0.3

// Floor 策略评分
score = 100 - ((cost - minCost) / (maxCost - minCost)) * 100

// Balanced 策略评分
score = price * 0.35 + speed * 0.35 + reliability * 0.3
```

### 配置示例

```yaml
# config.yaml
routing:
  default_strategy: balanced  # 默认策略

  # 策略特定配置
  nitro:
    ttft_weight: 0.7
    throughput_weight: 0.3

  balanced:
    price_weight: 0.35
    speed_weight: 0.35
    reliability_weight: 0.3

  # 场景规则
  scenarios:
    - name: chat
      strategy: nitro
      condition: "tokens < 100"

    - name: batch
      strategy: floor
      condition: "tokens > 1000"
```
